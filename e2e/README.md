# E2E(B4 結合確認)

実プロセスの API サーバー(UA・UB・UC のルートが同居)を一時 DB で起動し、HTTP で3ユニットを通して検証する。追加の依存パッケージは不要。

```bash
node --import tsx --test "e2e/*.test.ts"
```

- サーバーは空き TCP ポートと使い捨て DB(OS の一時ディレクトリ)で起動し、テスト終了時に停止・削除する。`data/` や他の開発サーバーには影響しない
- 起動時にシードが入る(メニュー12品、今日・昨日の注文)。テストは売上の「増分」で検証するのでシード値に依存しない
- 「今日」はサーバーの JST 日付。日付をまたぐ瞬間(JST 0:00 前後)に実行すると売上の日付判定でぶれる可能性がある

## シナリオ

| # | 内容 |
|---|------|
| 1 | 客が注文 → 厨房が調理中 → 完成 → 客の状況確認に反映 → 店長の売上に反映(合計・件数・商品別)。未完成の注文は売上に入らない。呼出番号の連番 |
| 2 | 店長の売り切れ設定 → 客のメニューに反映・注文は 409(部分注文なし)→ 解除で注文可。価格変更 → 新規注文は新価格、既存注文と売上は注文時点の価格。メニュー追加 → 客が注文可 |
| 3 | 1段階ずつしか進まない遷移、3ユニット共通のエラー形式、同時 10 注文での呼出番号重複なし、2端末の同時操作(200 + 409)、売り切れと注文の競合、未定義ルートの 404 形式(既知・#12) |
| 4 | 全シナリオ後の実 DB の不変条件(読み取り専用): completed_at と status の整合、total = 明細合計、呼出番号の日次一意、売上 API = DB 集計 |

## Web UI の E2E

Web UI のブラウザ操作は自動化していない(ブラウザ自動化の依存を追加しないため)。手順と結果は `aidlc-docs/construction/BOLT-REPORT-B4.md` に記録している。

再実施する手順:
1. `DB_PATH=data/e2e.db PORT=3100 npm run dev:server` と `API_PORT=3100 WEB_PORT=5273 npm run dev:web`
2. `/customer`(スマホ幅)で商品を選び「注文を確定する」→ 呼出番号が表示される
3. `/kitchen` の「受付」に注文が現れる → 「調理開始」→「完成」。客画面が自動で「調理中」「できあがり」に変わる
4. `/manager` の「売上」に完成した注文が反映される
5. `/manager` の「メニュー管理」で商品を売り切れにする → 客画面の新しい注文画面でその商品が注文不可になる
