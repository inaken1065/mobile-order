# セキュリティ要件: mobile-order の Google Cloud デプロイ

## Sources

- `[memory:M1]` `requirements.md` の NFR2（セキュリティ）、NFR7（互換性）、FR3（アクセス制限）、FR6（WIF）、FR7（課金の承認）
- `[Q1]` スモークテストと死活確認のパス。`[Q2]` ビルドとデプロイの経路。`nfr-requirements-questions.md` の回答
- `project.md` の ALWAYS / NEVER ルール（キーなし、WIF、自分の IP のみ、課金の承認）

## 認証・認可の方針

アプリにログイン機能はない（既存の仕様）。そのため、認可の代わりに「ネットワークの入口を自分の IP に絞る」ことで守る。アプリ側の認証は追加しない（範囲外）。

## 要件

| ID | 要件 | 合否の判定 | 出どころ |
|---|---|---|---|
| NFR2.1 | VM の 80 番は、変数で渡す自分の IP（CIDR）だけから許可する。それ以外の IP からは、画面にも `/api` にも届かない | 許可 IP 以外から `curl` が接続できない（タイムアウト）。ファイアウォールのルールに、許可 IP 以外の送信元からの 80 番がない | FR3.1、NFR2 |
| NFR2.2 | SSH（22 番）は IAP の範囲 `35.235.240.0/20` だけから許可する。インターネットの他の送信元（自分の IP を含む）からの直接の SSH はつながらない | ファイアウォールのルールで、22 番の送信元が `35.235.240.0/20` のみ。`gcloud compute ssh --tunnel-through-iap` で入れる | FR3.6、NFR2 |
| NFR2.3 | 開けるポートは 80 番（自分の IP）と 22 番（IAP の範囲）の 2 つだけにする。Fastify の 3000 番は外に開けない | `nmap` またはファイアウォールのルール一覧で、他のポートがない | FR3.5、FR4.2 |
| NFR2.12 | 既存コード `server/src/index.ts` は `0.0.0.0` で待ち受けを固定している。FR4.2（Fastify はローカルからの接続だけを受ける）を満たすため、最小限のコード変更を例外として認める(人間の指示)。サーバーの待ち受けアドレスを環境変数 `HOST` で指定できるようにし、未指定時は現状と同じ `0.0.0.0` とする。VM では systemd のユニットで `HOST=127.0.0.1` を指定する。既存テストは書き換えずに通す。ファイアウォールの 3000 番閉鎖(NFR2.3)との二重の防御とする | `HOST` 未指定のサーバーが `0.0.0.0` で待ち受け、既存テストが無修正で通る。VM 上で `ss -ltn` の 3000 番が `127.0.0.1` のみである。VM の外部から 3000 番に接続できない | FR4.2、レビュー R-01 |
| NFR2.4 | サービスアカウントキー（JSON キー）を作成も保存も使用もしない。GitHub のシークレットにも置かない | リポジトリと GitHub のシークレットに、`"type": "service_account"` を含む JSON がない。Terraform に `google_service_account_key` がない | FR6.2、NEVER ルール |
| NFR2.5 | GitHub Actions から Google Cloud への認証は、Workload Identity Federation だけを使う。許可条件は、このリポジトリの `main` ブランチ（`repository` と `ref` の両方）に限る。PR の CI は Google Cloud に認証しない | `main` 以外のブランチと他のリポジトリからの認証が失敗する。PR の CI のワークフローに `google-github-actions/auth` がない | FR6.1、FR6.3 |
| NFR2.6 | デプロイ用のサービスアカウントの権限は、IAP トンネルの利用、OS Login でのログイン、VM のサービスアカウントとしての利用の範囲に限る。`roles/editor` や `roles/owner` は付けない | 付与ロールの一覧が Terraform のコードにあり、上の範囲だけである | FR6.4 |
| NFR2.7 | 自分の IP、プロジェクト ID、その他の秘密情報を Git に入れない。変数ファイル（`*.tfvars`）は `.gitignore` に入れ、GitHub のシークレットか手元の変数で渡す | `git ls-files` に `*.tfvars` がない。`gitleaks` などで検査して 0 件 | NFR2、FR3.2 |
| NFR2.8 | HTTP のみ（暗号化なし）の通信を、学習用として受け入れる。リスクとして、注文内容が暗号化されずに自分の IP との間を流れることを記録する | `requirements.md` の NFR2 と、この文書にリスクとして書かれている | NFR2、`[Q4]`（要件定義） |
| NFR2.9 | `terraform apply` など課金が発生する操作は、実行のたびに、人間が `plan` の結果と見積もりを確認して承認してから、手動で実行する。CI は `apply` を実行しない | CI のワークフローに `terraform apply` がない。承認の記録（手順書のチェック）がある | FR7、ALWAYS ルール |
| NFR7.1 | VM の Node.js は 24 以上とし、バージョンを固定して入れる。起動時に `node --version` が 24 以上であること、`node -e "require('node:sqlite')"` が成功することを確認し、満たさなければ失敗とする。ランナーも同じバージョンに固定する | 起動スクリプトの確認が、24 未満や `node:sqlite` が読めない場合に失敗する。ランナーと VM のバージョンが一致する | NFR7、`[Q2]` |
| NFR7.2 | Node.js の配布物は、公式のものを使い、固定したバージョンのチェックサム（SHA-256）で検証してから入れる | 起動スクリプトにチェックサム検証があり、不一致なら失敗する | NFR7、NFR2（供給元の確認） |

## 脅威の考慮（簡易）

| 脅威 | 対策 |
|---|---|
| 他人が画面や API に触る | NFR2.1（自分の IP だけ） |
| 自分の IP が変わって別の人に割り当たる | FR3.3 の手順で許可 IP を更新する。変更前の IP は許可から外す |
| SSH への総当たり | NFR2.2（IAP の範囲のみ。インターネットから 22 番に届かない） |
| 鍵の漏えい | NFR2.4、NFR2.5（キーを持たない） |
| 通信の盗聴 | NFR2.8（受け入れたリスク） |

## Assumptions & Open Questions

- `[assumption]` A1: 自分の IP は固定に近く、変わる頻度が低い。
- 未確定: IAP の TCP 転送に追加の料金がないことは、A5（要件定義）に従い、実施時に公式情報で再確認する。
