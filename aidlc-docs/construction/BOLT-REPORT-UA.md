## 決定事項
- **売り切れ判定は注文トランザクション内**: `BEGIN IMMEDIATE` の中で `menu_items` を読み、売り切れなら 409、未知の id なら 400。判定後に売り切れへ変わる競合と、部分的な注文の残存を防ぐ。409 / 400 では `orders` / `order_lines` に何も残らない(テストで確認)
- **同じ商品の複数行は1行にまとめる**: 契約に規定はない。注文明細の重複を避けるため
- **qty の上限は設けない**: 契約(`minimum: 1`)に従う。上限が必要なら契約側の決定事項
- **呼出番号は日次リセットを採用**(当日 JST の `MAX + 1`): 飲食店の呼出番号は営業日ごとに 1 から振り直すのが自然で、`MAX + 1` のままだと番号が際限なく増えて客に読み上げにくい。`BEGIN IMMEDIATE` の中で採番するため重複しない。スキーマ変更は不要(`created_at` の先頭10文字で当日を判定)。**UNIQUE 制約はないので、同一日の重複防止はトランザクションに依存している**
- **エラー形式**: 客のルートのプラグインスコープで `setErrorHandler` を設定し、壊れた JSON など Fastify 自身のエラーも `{ "error": メッセージ }` に揃えた。5xx は内部メッセージを漏らさず `{ "error": "internal server error" }`。`app.ts` は未変更なので他ユニットのルートには影響しない
- **`GET /orders/:id` の不正な id(数値でない等)は 404**: 契約の応答は 200/404 のみのため
- **UI**:
  - 注文後の呼出番号・ステータスを 2 秒ごとにポーリング(READY で停止)
  - 通信エラー時は表示して再試行を継続
  - 注文 id を `localStorage` に保存し、リロードしても状況確認画面に復帰(`localStorage` が使えなくても動作する)
  - メニューは 10 秒ごとに再取得し、売り切れになった商品をカートから外す
  - 409 を受けたらメニューを取り直し、売り切れ商品をカートから外してメッセージを表示
  - 注文方式は「呼出番号」のみ(卓番号入力は実装していない)

## 実機確認(ブラウザ、幅 390px)
- カテゴリ別表示、売り切れ(杏仁豆腐)は「売り切れ」バッジで注文不可、カートが空のとき確定ボタン無効
- 数量の増減と合計(醤油ラーメン×2 + 生ビール = ¥2,250)
- 確定前に生ビールを売り切れにすると 409 → 画面にメッセージ、カートから生ビールが外れ ¥1,700 に更新
- 再確定で呼出番号 11 の状況確認画面 → 厨房の更新を DB で模擬すると 受付済み → 調理中 → できあがり へ自動更新
- リロード後も呼出番号 11(READY)が復元され、「新しい注文」でメニューに戻る。横スクロールなし

## 共通ファイルへの変更要望(編集していない)
1. **`package.json`**: ユニットのテストを実行するスクリプトがない。例: `"test:units": "node --import tsx --test \"server/test/*/*.test.ts\""`。B2・B3 のテストも同じ置き場なので、B4 で追加するのがよい
2. **`web/src/shared/api.ts`**: エラーが文字列(`"POST /orders -> 409 sold out: ..."`)のため、UI が正規表現でステータスを取り出している。`status` と本文を持つ `ApiError` を投げるようにしてほしい
3. **`server/src/app.ts`**: エラーハンドラを各ユニットのプラグインに置くと3箇所で重複する。アプリ全体の `setErrorHandler`(と未定義ルートの `setNotFoundHandler`)に集約すれば、`{ "error": ... }` を一元化できる。未定義ルートの 404 は現状 Fastify 標準の形式のまま
4. **契約テスト**: 呼出番号の日次リセットは契約テストの対象外(UA の受入テストでのみ検証)。他ユニットが依存しないため B0 の追加は必須ではない
