### E2E のシナリオ(`e2e/e2e.test.ts`)
1. 客が注文 → 厨房が調理中 → 完成 → 客の状況確認に反映 → 店長の売上に反映(合計・件数・商品別・内訳合計)。未完成の注文は売上に入らない。呼出番号の連番
2. 店長の売り切れ設定が客のメニューに反映され、注文は 409(部分注文なし)。解除で注文可。価格変更は新規注文のみに効き、既存注文と売上は注文時点の価格。メニュー追加が客に反映
3. 異常系・境界: 1段階ずつの遷移、3ユニット共通のエラー形式、同時 10 注文で呼出番号が重複しない、2端末の同時操作(200 + 409)、売り切れと注文の競合、未定義ルートの 404(既知・#12 の特性テスト)
4. 全シナリオ後に実 DB を読み取り専用で検査: completed_at と status の整合、`total` = 明細合計、日次の呼出番号一意、明細の重複行なし、売上 API = DB 集計

## 観察ポイント

- 足りなかった: ユニットテストの実行手段、OpenAPI の 400、API 経由の読み取り依存(`GET /menu`)。B0.1 で対応済み。B0 時点では実装がなく書けなかったものが多く、契約の「後から埋まる部分」を B0 の完了条件に明示しておけば計画内の作業にできた
- 入れすぎ: なし。シード・実サーバー・DB トリガーを B0 に入れたことで、B1〜B3 がモックなしで並列に進められた。差戻しで Wave 1 が止まることはなかった
- B1〜B3 が出した要望は計 5 件(うち 3 件が複数 Bolt の重複指摘)。**スキーマ変更を要する差戻しは 0 件**

### 縦割りで B1〜B3 の作業量は均等だったか
| ユニット | ルート | Web | テスト | 合計(行) | 受入テスト数 |

| UA 客 | 99 | 312 | 282 | 693 | 15 |

均等ではなかった。UC は UB の約 2.3 倍。UC は書き込み系 API が 3 つ + 入力検証 + 集計 + 2 タブの UI を持つのに対し、UB は 2 エンドポイントで UI も 1 画面。所要時間は各エージェントの実行時間で、UB は約 7.6 分だったが UA は約 4.0 分・UC は約 4.4 分と、行数に比例しなかった(UB の実行は他より長かった。原因は未分析)。縦割りは「ロール単位で完結する」利点がある一方、ロールごとの機能の厚みの差がそのまま Bolt の大きさの差になる。UC を「メニュー管理」と「売上」に分けると、より均等になる
