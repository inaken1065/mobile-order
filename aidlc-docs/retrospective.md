この文書は、リポジトリの記録(各 Bolt の報告書、PR、Issue、テスト結果)と作業中の経緯に基づく。**記録にないものは「推測」と明記する。** 数字の出典は末尾の「付録」。

## 1. ユニット分割の変遷: 横割り案 → 縦割り案

### 1.1 最初の案(横割り: サービス層と UI 層で分ける)
`02-units.md` の初版。

| ユニット | 内容 |
|----------|------|
| U0 | Contracts(型、OpenAPI、イベント、**モックサーバ**) |
| U1 | Menu Service |
| U2 | Order Service |
| U3 | Sales Service(`OrderCompleted` イベントを購読して日次集計) |
| U4 / U5 / U6 | Customer UI / Kitchen UI / Manager UI |

- 7 ユニット、Wave 1 は **6 Bolt を並列**(B1〜B6)、最後に B7 で結合
- ユニット間は契約(API・イベント)だけで結合。DB はユニットごとに別
- 並列性の源泉は **モックサーバ**: 各 Bolt は他ユニットをモックに向けて開発する
- 設計メモ(初版に記載): U2→U1 は同期 API 呼び出し(U1 停止時は注文不可と割り切る)、Sales は結果整合性

### 1.2 見直し後(縦割り: ロール単位)
ユーザーの指示で全面的に組み替えた。

| ユニット | 内容 |
|----------|------|
| U0 | Contracts + **ウォーキングスケルトン**(客画面のボタン → `POST /orders` → DB → 厨房画面を最小限で貫通) |
| UA 客 | メニュー閲覧 API・注文作成 API + Customer UI |
| UB 厨房 | 注文一覧 API・ステータス更新 API + Kitchen UI |
| UC 店長 | メニュー管理・売り切れ・売上集計 API + Manager UI |

- 4 ユニット、Bolt は B0 → B1〜B3(並列)→ B4(結合)
- **API サーバー 1 つ・DB 1 つ(SQLite)**。ロールごとにルートモジュールを分ける
- 売上はイベントを使わず、完成した注文を DB から集計する
- 並列性の源泉は **U0 が用意する実サーバー・実 DB・シードデータ**(モック不要)

### 1.3 判断理由
**ユーザーが明示した変更点**は上の構造(ロール単位の縦割り、単一サーバー・単一 DB、イベントなし、ウォーキングスケルトン)で、**理由そのものはやり取りの中では述べられていない**。以下は、その時点で `02-units.md` の比較メモに記録した評価と、実際に進めた結果からの分析(一部は推測)。

| 観点 | 横割り | 縦割り |
|------|--------|--------|
| ストーリーの完結 | 1 ロールの機能が 3〜4 ユニットに散る | 1 ロール = 1 Bolt で、デモ可能な単位になる |
| 結合の場所 | API・イベント境界(ネットワーク、結果整合性) | テーブル境界(同一 DB、同一プロセス) |
| 並列の前提 | モックサーバを作り、実装との乖離を管理する | U0 が実物とシードを用意するだけ |
| 運用の複雑さ | 3 サービス + イベント基盤を学習用に抱える | 1 プロセスで済む |
| 代償 | モックと実装のずれ、結果整合性の議論 | U0 に責務が集中する。共有テーブルの**書き込み権限の線引き**が必要 |

- 「学習目的が Bolt 並列の体験なのに、サービス分割の分散システム的な論点(イベント、結果整合性、モック乖離)に注意が奪われる」ことを避けられた(推測。ユーザーの意図として確認はしていない)
- 縦割りで消えた問題と、新しく生まれた問題がある。生まれた問題は次節以降で詳述する
  - 消えた: モックと実装の乖離、イベント、結果整合性、サービス間の同期呼び出し
  - 生まれた: **共有 DB のテーブルを誰が書くか**、U0 の肥大化、ロールごとの作業量の不均等

### 1.4 縦割りの帰結(実績)
- **作業量は均等にならなかった**: UA 693 行 / UB 457 行 / UC 1,037 行(ルート + Web + テスト)。UC は UB の約 2.3 倍。UC は書き込み系 API 3 つ + 入力検証 + 集計 + 2 タブの UI を持つ。縦割りは「機能の厚み」がそのまま Bolt の大きさになる
- **U0 の責務は想定どおり重く、それが効いた**: スキーマ、トリガー、シード、契約テストを B0 に集めたことで、B1〜B3 が一度も止まらなかった
- 時間の観測(各エージェントの実行時間。準備・レビュー・マージは含まない): UA 約 4.0 分、UB 約 7.6 分、UC 約 4.4 分。並列の実時間は最長の約 7.6 分で、直列なら合計約 16 分。**行数と時間は比例しなかった**(UB が最長。原因は未分析)

## 2. 並列 Bolt で実際に起きたこと

### 2.1 起きなかったこと(確認できた範囲)
- **ファイル衝突はなかった**。3 PR の変更ファイルを機械的に確認し、すべて自ユニットの範囲内(ルート、`server/test/<role>/`、`web/src/<role>/`、報告書)。3 PR ともコンフリクトなしでマージ可能
- **担当表の違反は記録されていない**。DB 書き込み担当表(トリガー + 静的検査)に違反した実装はなかった
- **契約テストが Wave 1 で赤になった記録はない**。3 Bolt とも PR 作成前に全件緑と報告

> 注意: 「違反が起きなかった」ので、担当表と契約テストが**実際に違反を止めた**事例は、この開発では観測されていない。効果の根拠は「検出能力があること(ミューテーション検査 22 件、E2E 変異 5 件を検出)」であり、「実際に止めた回数」ではない。

### 2.2 実際に起きた問題
Wave 1 から共通ファイル・契約への変更要望が出た。これが「並列で実際に起きた問題」の中心。

| # | 内容 | 出典 | 原因の分類 | 結果 |
|---|------|------|-----------|------|
| 1 | ユニットテストを実行する npm スクリプトがない | B1・B2・B3 | 開発基盤の不足 | B0.1 で対応 |
| 2 | OpenAPI に実装が返す 400 が未定義 | B2・B3 | 契約の記述漏れ(B0 時点では実装がなく書けなかった) | B0.1 で対応 |
| 3 | UC の UI が UA の `GET /menu` に依存している(店長用一覧 API がない) | B3 | **設計上の暗黙依存**(B0 の「暗黙の結合」3 点に入っていなかった) | B0.1 で契約化 |
| 4 | `web/src/shared/api.ts` のエラーが文字列で、UI が正規表現でステータスを取り出している | B1 | 共通基盤の品質 | backlog #11 |
| 5 | エラーハンドラを各ユニットが重複して実装している(未定義ルートの 404 だけ形式が違う) | B1・B2 | 共通基盤の品質 | backlog #12 |

並列で表面化した別の現象:
- **同じ判断を3回する**: エラー形式の統一(`{ error }`)を、共有の `app.ts` を触れない制約のため UA・UB・UC がそれぞれプラグイン内で実装した。共通ファイルを読み取り専用にした代償として、重複が生まれた(#5)
- **UI の回避策**: Customer UI は、`api.ts` を直せないためエラー文字列を正規表現で解析する実装になった(#4)。共通ファイル凍結の副作用で、技術的負債が各ユニットに分散した
- **契約外の判断が各ユニットで決まった**: 呼出番号の日次リセット(UA)、重複行の合算(UA)、同一状態への遷移は 409(UB)、メニュー入力の検証規則(UC)など。他ユニットや B4 に影響するものは B0.1 で契約に昇格した。**これらは各エージェントが「妥当と判断した」もので、人間の合意を取った決定ではない**

### 2.3 B0 の段階(並列の前)で起きたこと
- **契約テストの穴**: ミューテーション検査で、テスト 3 の「売上の日付は `completed_at` 基準」が `created_at` 基準の実装と区別できていなかった。注文を作る時刻が実時刻で、実行日が固定値と偶然同じだったため通っていた。注文の `created_at` を指定できるヘルパーを追加して解消
- **等価変異**: 売上の `status = 'READY'` 条件だけを緩める変異は結果が変わらなかった。`completed_at` が READY 以外では常に NULL(トリガーで保証)なので、日付条件が除外する。多重防御の副作用で、検出対象外とした
- 変異検査は 19 → 22 件に増え(B0.1 で 0d 関連 3 件)、E2E 側にも 5 件を実施

### 2.4 契約・担当表・契約テストがどう効いたか

| 仕組み | 効いたこと | 効かなかった・限界 |
|--------|-----------|-------------------|
| **ウォーキングスケルトン + 実サーバー + シード** | B1〜B3 がモックなしで、自分のポート・DB で並列に開発・結合確認できた | — |
| **書き込み担当表 + DB トリガー** | 注文の不変列・遷移・`completed_at` の規則を、アプリのコードに依存せず DB が守った。UB の `transitionOrder()` 経由に更新を絞れた | 実行時にユニットを識別できない(1 プロセス・1 DB)ので、境界はトリガーと静的検査のみ |
| **静的検査(契約テスト 0b)** | ルートファイルごとの書き込み SQL を許可リストで検査 | SQL を大文字で書く規約に依存。クエリビルダ導入時は更新が必要 |
| **契約テスト 1〜3(暗黙の結合 3 点)** | menu_items の列、`orders.status` の値、売上は READY のみ、をユニット境界で固定 | **API 経由の結合(`GET /menu` の全件保証)は想定外だった** → B0.1 で 0d を追加 |
| **「共通ファイルは読み取り専用」ルール** | 3 ユニットとも誰も共通ファイルを編集せず、要望を報告に集約。変更が B0.1 に一本化された | 重複実装(§2.2)という代償 |
| **PR 単位の編集範囲チェック** | 各 PR の変更ファイルを機械的に確認でき、範囲外の変更がないと言い切れた | — |
| **ミューテーション検査** | 契約テストの穴を 2 件(B0 のテスト 3、B4 の E2E の並び)発見。**「テストが通る」と「テストが効く」は別**と確認できた | 等価変異の判別は人間が必要 |

## 3. B4 で見つかった結合の問題

### 3.1 結果: 統合で新たに見つかったバグは 0 件
- API 経由の E2E 14 件、契約テスト 27 件、ユニットテスト 69 件がすべて通過
- Web UI は 390px 幅でブラウザ操作(客の注文 → 厨房で完成 → 売上 ¥7,100 / 4 件が期待値と一致 → 売り切れが客に反映)。コンソールエラーなし。**UI は手動確認で、自動化していない**
- ユニットのコードは変更していない

### 3.2 見つかったのは E2E テスト自身の穴
最初の E2E は、変異 5 件のうち 1 件(厨房の一覧を新しい順にする)を検出できなかった。E2E が `status` 指定の一覧の並びしか見ておらず、実際の Kitchen UI が使う指定なしの一覧は未検証だった。検証を追加して 5/5 検出になった(契約テスト 2c は元から両方を検証していたので、重なりで補えてはいた)。

### 3.3 「バグ 0 件」をどう読むか(過信しないために)
「0 件」は、結合が完璧だったことの証明ではない。以下の理由で、見えていない問題がありうる。

- **独立性が低い**: 3 つの Bolt は、同じモデルの分身(会話の文脈を引き継いだ並列エージェント)で、同じ前提・同じ癖を共有していた。実際のチームなら別々の人が別の解釈をして、結合時にずれが出る。**この開発では「並列実行の効率」は体験できたが、「並列実行の解釈のずれ」はほとんど体験できていない**
- **同じ作者が契約・実装・テストを書いた**: 3 者の死角が一致しうる
- **検証していない領域**: 日付をまたぐ瞬間(JST 0:00 前後)、複数台の実機、長時間の運用、負荷、認証、アクセシビリティ、UI の自動テスト
- **E2E の大半は API レベル**で、UI の結合(状態の持ち方、ポーリングのタイミングなど)は手動の 1 回の確認のみ

### 3.4 契約・スキーマで防げたもの / 防げなかったもの
- 防げた(結合時に食い違いが出なかった): menu_items の列、status の値、売上の集計対象、越境書き込み
- 防げなかった(Wave 1 の途中で表面化): API 経由の読み取り依存(§2.2 の #3)、エラーレスポンスの記述漏れ(#2)、テスト実行基盤(#1)

## 4. 次に同じような開発をするとき、最初から決めておくべきこと

### 4.1 分割と契約
1. **分割軸と共有物の方針**(縦割り/横割り、DB・サーバーを共有するか)を、最初に比較表で決める。縦割りなら「U0 に責務が集中する」ことを前提に B0 の規模を見積もる
2. **結合の種類を網羅して書き出す**: DB 経由(書き込み担当表)だけでなく、**API 経由の読み取り依存**、イベント、共有ファイルも。「他ユニットのルートを読み取りで使うか」を各ユニットに問う
3. **契約の「後から埋まる部分」を B0 の完了条件に明記する**: 全エンドポイントのステータスコード(400・404・409 を含む)、エラー形式、入力検証の規則。B0 では実装がなく書けなかったものが多く、差戻しになった
4. **曖昧な要件を先に決める**: 同一商品の重複行の扱い、数量の上限、不正な id の扱い、呼出番号の採番規則(日次リセットか)、日付の基準。今回は各エージェントの判断に任せ、事後に契約へ昇格した

### 4.2 共通基盤(B0 に入れる)
5. **エラー形式とエラーハンドラを `app.ts` に共通実装する**(全体の `setErrorHandler` と `setNotFoundHandler`)。共通ファイルを凍結するなら、凍結する前に共通部分を完成させる。そうしないと重複実装になる(#12)
6. **Web の API クライアントを `ApiError`(ステータスと本文を持つ)で作る**(#11)
7. **テスト実行基盤**: ユニットテスト・E2E の npm スクリプト、`tsconfig` の `include`、並列実行用のポート・DB の環境変数を B0 に入れる
8. **時刻の扱い**: タイムゾーン(JST 文字列)と「日付」の定義、**時計の注入**(テストで「今日」を固定できるようにする)。日付境界のテストが実時刻に依存しないように
9. **UI の自動 E2E の方針**(Playwright 等を入れるか)を B0 で決める。後から入れるには共通ファイル(`package.json`)の変更が要る

### 4.3 並列実行の運用
10. **変更要望の受付経路を先に決める**: 「共通ファイルは編集せず報告する → B0.x にまとめて反映する」というルールは機能した。分類(基盤の不足/契約の記述漏れ/設計の暗黙依存/品質)のテンプレートと、緊急時(Wave を止める基準)も最初に決める
11. **Bolt の大きさを揃える**: 縦割りでは機能の厚みの差が出るので、UC のように重い Bolt は先に分割する(例: メニュー管理 / 売上)
12. **並列の独立性をどう確保するか**: 同じモデルの分身では解釈のずれが出にくい。学習目的で「ずれ」を体験したいなら、Bolt ごとに異なる指示・制約を与える、結合前に人間がレビューする、などを設計する
13. **決定の記録**: 各 Bolt が契約外で決めたことを必ず報告書に書かせ、**人間が合意するゲート**を置く(今回は事後に B0.1 で契約へ昇格した)
14. **環境の分離を手順化**: ポート・DB・ブラウザコンテキスト(`isolatedContext`)の分離は機能したが、毎回指示文に書いた。スクリプト・README に落とす

### 4.4 テストの質
15. **ミューテーション検査を契約テストの完成条件に入れる**。「通る」だけでなく「壊すと赤になる」を確認する(今回 2 件の穴を発見)
16. **等価変異の扱いを決める**: 多重防御で結果が変わらない変異は検出対象外とし、理由を記録する
17. **「実際に止めた」実績を残す**: 担当表や契約テストが違反を検出した事例(または違反の注入実験)を記録し、効果を数字で言えるようにする

### 4.5 プロセス・ドキュメント
18. **スカッシュマージを前提にした運用**: ブランチは `git branch -D` で削除する必要がある(通常の `-d` は未マージと判定する)。Issue のクローズは PR の `Closes #` に任せ、手動クローズ(B0 の例)は理由を残す
19. **ドキュメントの陳腐化**: README の実装状況の表は Wave 1 の完了で古くなり、B0.1 で更新した。実装状況の表は Bolt の完了条件に含める
20. **スコープ外を最初に書く**(認証、決済、複数店舗)。今回は決めたが、結合の議論でしばしば再確認が必要だった
